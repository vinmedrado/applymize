# Auditoria completa — Applymize

Data: 27/07/2026

Branch auditada: `main`

Commit auditado: `4a92772d5a712c2e35c967d46ebf52d430691791`

## Veredito executivo

O Applymize tem uma base full-stack funcional, bem documentada e visualmente forte. O ambiente pessoal/local está operacional, os 123 testes de backend passam, o banco está no último head do Alembic e o frontend gera um artefato estático de produção válido.

O caminho para transformar o frontend em portfólio no Netlify está pré-configurado pelo `netlify.toml`, mas o deploy ainda não existe: não há site Applymize na conta Netlify autenticada e o diretório local não está vinculado a um projeto.

Antes de publicar, a experiência pública precisa ser realinhada com a decisão do projeto. A landing e a página de planos ainda promovem cadastro, login, venda B2C/B2B e um “SaaS monetizável”, embora o backend continue privado/local. Em um Netlify somente estático, esses CTAs levam a fluxos sem backend e passam uma impressão de produto quebrado.

Também há pendências atuais de segurança de dependências e do ambiente local. O `npm audit` encontrou 3 vulnerabilidades altas. O `pip-audit` encontrou 67 ocorrências em 8 pacotes Python, com vários registros duplicados ou dependentes de recursos que o projeto não usa, mas com riscos aplicáveis em parsers de arquivos e multipart. Além disso, serviços locais estão publicados em todas as interfaces com credenciais previsíveis.

## Pendências priorizadas

### P0 — antes do deploy do portfólio

#### 1. Corrigir o posicionamento e os CTAs públicos

Problema:

- landing descreve uma “experiência SaaS moderna”;
- `/pricing` se apresenta como “SaaS monetizável”, venda B2C e expansão B2B;
- botões públicos enviam recrutadores para cadastro, login e planos;
- no Netlify estático, cadastro, login, recuperação de senha e dashboard não terão backend;
- a página de planos afirma que, com Stripe, o sistema usa Price IDs e webhooks, mas o backend ainda retorna um placeholder.

Ação recomendada:

- reposicionar a landing explicitamente como case de portfólio e ferramenta pessoal;
- priorizar “Como funciona”, “Testar ATS”, “Ver demo” e “Ver código no GitHub”;
- remover ou identificar `/pricing` como conceito visual legado, sem promessas de checkout;
- remover “Criar conta/Entrar” da jornada principal pública ou identificá-los como ambiente privado/local;
- incluir autoria, GitHub, LinkedIn e contato no footer.

#### 2. Atualizar dependências do frontend

Resultado atual do `npm audit`:

- 3 vulnerabilidades altas;
- `postcss`;
- `react-router` e `react-router-dom`.

O advisory do React Router está relacionado ao modo RSC, que esta SPA Vite não utiliza, portanto a exploração não foi demonstrada no Applymize. Ainda assim, a dependência deve ser levada para uma versão segura e a regressão de rotas precisa ser validada.

Ação recomendada:

- atualizar PostCSS e React Router para versões não afetadas e compatíveis;
- executar `npm ci`, lint, build, `npm audit` e smoke das rotas;
- recriar o container frontend para atualizar o volume de dependências.

#### 3. Criar e vincular o site no Netlify

O `netlify.toml` já está correto para o objetivo estático:

- base `frontend`;
- comando `npm run build`;
- publicação `dist`;
- Node 22;
- fallback SPA;
- headers básicos.

Ação recomendada:

1. criar um novo site Netlify conectado a `vinmedrado/applymize`;
2. usar `main` e deixar o `netlify.toml` controlar o build;
3. não configurar `VITE_API_BASE_URL` para o portfólio estático;
4. validar todas as rotas diretas, upload local, ATS e responsividade;
5. adicionar a URL ao README e à homepage do GitHub.

#### 4. Proteger o ambiente pessoal/local

Estado encontrado:

- PostgreSQL, Redis, Evolution API, FastAPI e frontend publicados em `0.0.0.0`;
- Redis sem autenticação;
- PostgreSQL e Evolution com credenciais locais previsíveis e documentadas;
- `.env` usa os segredos JWT de exemplo;
- integração Groq e notificações estão configuradas no ambiente real;
- scheduler e notificações estão habilitados.

Ação recomendada:

- gerar novos `SECRET_KEY` e `REFRESH_SECRET_KEY`;
- trocar a chave da Evolution API;
- publicar PostgreSQL, Redis e Evolution somente em `127.0.0.1` ou não publicar suas portas;
- restringir API e frontend a loopback, salvo quando acesso LAN for conscientemente necessário;
- se houver acesso LAN, expor somente frontend/API, com firewall e segredos fortes;
- nunca expor essa composição diretamente na internet.

### P1 — alta prioridade depois do deploy inicial

#### 5. Atualizar dependências Python com regressão

O `pip-audit -r requirements.txt` encontrou 67 ocorrências em 8 pacotes:

- diretos: `PyJWT`, `python-dotenv`, `requests`, `pytest`, `pypdf` e `python-multipart`;
- transitivos: `markdownify` e `starlette`.

Nem todos os advisories são aplicáveis. O Applymize usa HS256 fixo e não usa JWK/JWKS, algoritmos mistos, RSC ou vários dos recursos citados. São aplicáveis, porém, as superfícies de upload PDF e multipart caso o backend fique acessível em rede. A versão atual do Starlette também pode afetar verificações baseadas em `request.url.path`, usado pelo rate limiter.

Ação recomendada:

- atualizar FastAPI para trazer uma versão compatível e corrigida do Starlette;
- atualizar PyJWT, Requests, python-dotenv, pypdf e python-multipart;
- separar pytest e demais ferramentas de teste das dependências de runtime;
- repetir os 123 testes, smoke de upload PDF/DOCX/TXT e `pip-audit`.

#### 6. Criar CI mínimo no GitHub Actions

Pipeline recomendado:

1. backend: instalação limpa, compilação, `pip check`, migrations e `pytest`;
2. segurança Python: `pip-audit`;
3. frontend com Node 22: `npm ci`, lint, build e `npm audit`;
4. validação de `docker compose config`;
5. bloqueio de merge quando testes/build falharem.

#### 7. Adicionar testes do frontend

Prioridade de cobertura:

- motor `publicAtsEngine.ts`;
- extração e erros de PDF, DOCX e TXT;
- cálculo de palavras-chave, senioridade e aderência;
- fallback e transparência da demo;
- rotas públicas;
- fluxo “Usar exemplo → Analisar agora”;
- teste E2E mínimo do build estático.

#### 8. Corrigir a eficiência da automação/providers

Nas últimas 24 horas:

- 68 execuções por provider para quatro termos de busca;
- 28 execuções JobSpy falharam e 40 terminaram com coleta parcial;
- Google respondeu repetidamente com HTTP 429;
- 408 registros de provider por dia foram gerados;
- somente 2 novas vagas foram inseridas;
- cada termo registrou erro em todas as execuções agregadas.

Ação recomendada:

- permitir excluir JobSpy/Google da automação;
- aplicar cooldown/circuit breaker depois de 429;
- não repetir três tentativas para cada termo quando a origem já bloqueou o IP;
- reduzir frequência ou termos redundantes;
- distinguir “sucesso com warning” de “erro” em `provider_runs`;
- criar métricas de taxa de inserção, duração e falha por provider.

#### 9. Melhorar apresentação e descoberta no GitHub

- atualizar a descrição do repositório;
- adicionar URL do Netlify na homepage;
- adicionar tópicos coerentes;
- inserir screenshot ou GIF e link da demo no topo do README;
- incluir autoria e contato;
- decidir conscientemente se haverá licença;
- configurar Dependabot ou Renovate.

#### 10. Adicionar SEO básico ao frontend estático

O `index.html` possui apenas título, favicon, viewport e theme color.

Ação recomendada:

- meta description;
- Open Graph e Twitter Card;
- imagem social;
- canonical após definir a URL;
- `robots.txt` e `sitemap.xml`;
- títulos e descrições por rota, se desejado;
- Content Security Policy compatível com PDF worker e estilos usados.

## Arquitetura e segurança

### Pontos fortes

- autenticação revalida usuário, membership e tenant;
- endpoints privados revisados usam `get_auth_context`;
- consultas principais filtram `tenant_id` e, quando necessário, `user_id`;
- admin exige role owner/admin;
- tokens de refresh são separados dos tokens de acesso;
- arquivos e chaves não são enviados pelo frontend público do laboratório ATS;
- HTML do currículo moderno escapa conteúdo do perfil;
- erros internos são registrados no backend e retornam mensagem genérica;
- integrações externas revisadas usam timeout.

### Limitações mantidas por decisão

- billing real não será prioridade enquanto o projeto continuar como portfólio/ferramenta pessoal;
- Recruiter e planos são demonstrações, não produto empresarial;
- scheduler em thread e rate limit em memória são aceitáveis apenas no processo local único;
- backend não deve ser publicado apenas para ativar login no portfólio;
- credenciais em armazenamento web são toleráveis no uso pessoal, mas não seriam a opção preferida para uma aplicação pública.

## Artefato de produção

O build Vite foi aprovado, mas reporta chunks grandes:

- worker PDF: aproximadamente 1,25 MB;
- chunks JavaScript: aproximadamente 531 kB, 503 kB e 477 kB;
- CSS: aproximadamente 54 kB.

PDF e DOCX são carregados sob demanda, reduzindo o impacto inicial, mas ainda há oportunidade de dividir melhor o bundle principal por rota.
