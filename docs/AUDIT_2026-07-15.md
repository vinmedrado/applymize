# Auditoria técnica e de produto — Applymize

Data: 15/07/2026

## Veredito executivo

O Applymize está pronto para uso local contínuo e demonstrações funcionais pelo Docker Desktop. A jornada principal foi validada no PostgreSQL real e os cinco serviços chegam ao estado operacional esperado.

O projeto ainda não está pronto para ser vendido ou exposto diretamente na internet como SaaS de produção. Os principais bloqueadores são cobrança Stripe incompleta, ausência de autorização por plano no módulo Recruiter, segredos locais previsíveis, falta de HTTPS/backup/monitoramento e frontend servido pelo Vite em modo de desenvolvimento.

## Escopo revisado

- Produto atual: `backend/`, `frontend/`, `migrations/`, `tests/`, `scripts/` e Docker Compose.
- Infraestrutura: PostgreSQL, Redis, Evolution API, API FastAPI e frontend Vite.
- Documentação: `README.md`, `SETUP.md`, `.env.example` e documentos em `docs/`.
- Código legado: `app.py`, `run.py`, `core/`, `automation/`, `intelligence/`, `scrapers/` e `legacy/`.
- Total inventariado: 306 arquivos relevantes, sem contar `node_modules`, `dist` e caches.

## Resultado das validações

- Backend: 114 testes aprovados.
- Python: compilação aprovada, `pip check` sem dependências quebradas.
- Banco: Alembic em `0019_user_automation_cascade`, igual ao `head`.
- Frontend: TypeScript/lint aprovado e build Vite aprovado.
- Dependências frontend: 6 vulnerabilidades inicialmente encontradas; lockfile atualizado; `npm audit` final com 0 vulnerabilidades.
- HTTP: frontend, `/health` e `/docs` responderam 200.
- Containers: banco, Redis, Evolution, API e frontend validados como `healthy`; todos usam `restart: unless-stopped`.
- Logs: nenhuma ocorrência nova de traceback, erro fatal ou violação de integridade depois da recriação e do smoke test.
- A consulta externa de CVEs Python com `pip-audit` não terminou por latência do índice. Isso não invalida `pip check`, mas deve ser repetido em CI.

## Jornada validada como cliente

Foi criada uma conta temporária no ambiente Docker e executado o fluxo:

1. Cadastro e autenticação.
2. Consulta da conta/tenant.
3. Criação de vaga manual, preservando o título digitado.
4. Matching com score 94,25.
5. Carregamento do dashboard.
6. Conclusão do onboarding.
7. Exclusão definitiva da conta.
8. Reutilização do token antigo recusada com HTTP 401.

A conta e seus dados temporários foram removidos ao final.

## Problemas corrigidos durante a auditoria

- Porta interna do PostgreSQL corrigida de `5434` para `5432` na conexão entre containers.
- Reinício automático e healthchecks adicionados/ajustados em toda a stack.
- API agora aguarda banco e Evolution saudáveis; frontend aguarda a API saudável.
- URL da API no frontend deixou de depender de um IP fixo da rede local.
- Sessão expirada agora limpa tokens e retorna ao login.
- JWT do WebSocket deixou de viajar na query string e, portanto, nos access logs.
- WebSocket passa a revalidar a conta e encerra corretamente após exclusão do usuário.
- Exclusão de conta corrigida com cascade nas tabelas de automação e teste de regressão.
- Corrida concorrente no matching protegida por lock transacional no PostgreSQL.
- Healthcheck passou a consultar o banco e não expõe configuração CORS/ambiente.
- Token/link de redefinição de senha deixou de ser escrito em log.
- Preferências do perfil não sobrescrevem filtros explícitos de busca de vagas.
- Upload de currículo passa a adotar o nome provável extraído quando apropriado.
- Termos técnicos compostos, como Power BI, são preservados na tradução.
- Vagas manuais preservam capitalização e texto digitado pelo usuário.
- Testes deixaram de acessar providers externos e usam banco SQLite isolado em memória.
- Lifecycle do FastAPI migrado de `on_event` para `lifespan`.
- Dependências frontend corrigidas e build Docker tornado determinístico com `npm ci`.
- README/SETUP corrigidos para porta 8001, execução destacada, providers atuais e comandos dentro do Docker.

## Bloqueadores para produção comercial

### Críticos

1. **Billing não processa pagamento real.** Sem Stripe, o endpoint altera o plano do tenant diretamente; com Stripe configurado, ainda retorna um placeholder. Faltam Checkout Session, webhook assinado, persistência da assinatura, cancelamento e reconciliação.
2. **Entitlements e RBAC incompletos.** O painel Recruiter exige apenas autenticação e isolamento por tenant; não exige plano Recruiter/Enterprise nem uma role específica. O menu comercial também aparece para todos os usuários.
3. **Segredos e credenciais locais.** Compose e `.env.example` usam senhas/chaves previsíveis para desenvolvimento. Produção precisa usar secrets fortes e falhar no startup se valores de exemplo forem detectados.
4. **Infraestrutura pública ausente.** Não há reverse proxy HTTPS, política testada de backup/restore, monitoramento externo, alertas, rotação de logs nem plano de recuperação.
5. **Estado do Git.** Quase todo o produto moderno aparece como não rastreado no repositório. Sem commit/versionamento confiável, uma máquina nova, deploy ou rollback pode ficar incompleto.

### Altos

1. O frontend usa servidor Vite de desenvolvimento e bind mount; produção deve gerar artefatos estáticos e servi-los por Nginx/Caddy/CDN.
2. A imagem `evoapicloud/evolution-api:latest` não está fixada por versão/digest, permitindo mudanças inesperadas.
3. O scheduler roda em thread dentro da API. Mais de um worker/replica pode duplicar execuções; deve virar worker/serviço separado com lock distribuído.
4. Rate limit e caches são locais ao processo. Para múltiplas réplicas, devem usar Redis.
5. Providers externos podem falhar, mudar HTML/API ou impor limites. São necessários timeouts, métricas, circuit breaker e acompanhamento de termos de uso por fonte.
6. O build completo `docker compose up -d --build` teve download muito lento nesta máquina e foi cancelado; a stack final foi recriada com as imagens existentes. O build TypeScript/Vite e o lockfile passaram separadamente, mas um clean build deve fazer parte do CI.

### Médios

1. Há 12 avisos de configuração Pydantic V2 e um aviso do `passlib` sobre `crypt`, relevante antes de Python 3.13/Pydantic 3.
2. Login e cadastro vêm preenchidos com credenciais/dados de demonstração; útil em demo, inadequado para produção.
3. O menu tem muitos módulos no mesmo nível e mistura carreira, operação, admin e Recruiter. Recomenda-se navegação por persona e plano.
4. O bundle principal tem cerca de 472 kB (134 kB gzip); code splitting por rota reduzirá o primeiro carregamento.
5. O protótipo Streamlit permanece duplicado (`app.py` e `legacy/streamlit_app.py`) junto a módulos antigos. O arquivo residual local `dy` foi confirmado como uma resposta de erro sem uso e ficou fora do versionamento.

## Documentação

O README agora está correto para o ambiente atual: frontend em 5173, API em 8001, comandos Docker, reinício automático, lista dos seis providers e limites comerciais explícitos. O `SETUP.md` também usa comandos executados dentro do container, que é o ambiente realmente reproduzível.

## Próximas etapas recomendadas

1. Manter todo o produto atual em um commit-base revisado; a deduplicação do legado deve ocorrer depois, em mudança separada e reversível.
2. Implementar Stripe e uma matriz central de permissões por plano/role antes de aceitar clientes pagantes.
3. Criar perfil Compose/CI de produção com frontend estático, imagens fixadas e secrets externos.
4. Automatizar backup + teste de restore e adicionar monitoramento/alertas.
5. Separar scheduler em worker e mover rate limit/cache para Redis.
6. Adicionar CI com clean build, 114 testes, lint/build, `npm audit` e `pip-audit`.
